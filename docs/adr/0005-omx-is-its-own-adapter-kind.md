# OMX is its own Adapter kind

Chunk 1 of the multi-agent console decided that one `codex` kind recognises both `codex` and `omx` processes: OMX (oh-my-codex) wraps the Codex TUI, so the title rule, prompt submission, turn capture and conversation lookup were identical, and one kind was the smallest change. Two facts made that untenable. First, adapter configuration gives one global program per kind, so a deployment could not run plain Codex in some worktrees and OMX in others — the live config pointed `adapters.codex` at plain Codex and OMX became unlaunchable from the console. Second, every OMX-only rule — worker-pane exclusion, HUD cleanup, orphan workers, the structured question files, and the ZFS session-pointer `setup`/`teardown` — hung off the Codex kind, so a configured teardown also fired for plain Codex stops and an OMX agent was badged Codex. We chose to make `omx` its own kind with its own Adapter, config entry, launch memory, badge and cleanup rules, while sharing the Codex TUI behaviours by reference (one `codex-tui.ts` helper both Adapters carry). We chose this because the two differ exactly where the Adapter interface already separates concerns — recognition, launch composition, questions, pane rules — and are identical exactly where the interface lets one object serve two kinds; a per-Worktree or per-Project program override would have solved only the launch half and left the misattributed rules in place.

## Considered options

- **Keep one kind, add a per-Worktree program override.** Solves "OMX here, Codex there" but every OMX rule still fires for plain Codex, the badge stays wrong, and the launch memory cannot remember "OMX" because there is nothing to remember.
- **One kind with a `variant` field on the agent.** The recognizer would tag each pane `codex`/`omx` and every consumer would branch on the variant. That is a second kind wearing a different name, without the exhaustive `Record<AgentKind, …>` checks that make adding a kind mechanical.
- **Recognise OMX by its Codex child and infer the wrapper afterwards.** Fragile: the wrapper is the process that identifies OMX (the child is plain `codex -c …`), and the walker already checks a pane's tree top-down, so meeting the wrapper first is the natural recognition.

## Consequences

- **Recognition is by the wrapper ancestor.** OMX 0.21.0 launches Codex as a direct child of `node …/oh-my-codex/dist/cli/omx.js` and stays alive as its parent; the walker claims the pane at that node process before reaching the Codex child, so no ordering trick in the registry is needed. Whether an OMX process is an Agent is decided from the first argument after the entry, exactly as OMX's own dispatcher decides its command: absent, `launch`, `resume`, or any `--flag` is the launch, and any other first argument (`hud`, `team`, `sidecar`, `mcp-serve`, …) names a helper. Console launches lead with `--direct`, so an operator flag with a value after it cannot hide the Agent. The Codex recognizer no longer matches `omx`, which required moving it into a leaf module so the Codex Adapter no longer imports the process walker (which imports the registry, which imports every Adapter): both Adapters hold the shared `codex-tui.ts` objects at load time, and that only works while the import graph stays acyclic.
- **The Adapter owns `--direct`.** Inside tmux, OMX's default policy manages HUD panes the console would classify as cleanup targets; `--direct` yields the direct policy even with `$TMUX` set. `--direct` and `--tmux` are reserved arguments, dropped from `adapters.omx.args` with a boot warning like Claude's reserved flags.
- **Bookmarks stay pinned to their recorded kind.** Every existing bookmark is `codex` and resumes in plain Codex; a bookmark taken under OMX records `omx`. There is no cross-kind resume.
- **The Codex-only features stay on the Codex entry.** Review tour, ChatGPT accounts, update advisor and the app-server command catalog read `adapters.codex`; an OMX-only configuration does without them. A `codex` entry whose program is OMX (the pre-split configuration) warns at boot and in `config:check`; the Projects migration is untouched.
- **One agent-agnostic scan fact.** `PaneScan.excluded(pane)` is the registry's answer to "does any Adapter hide this pane", so the Codex stale rule skips OMX worker panes without naming OMX's worker paths, and the OMX leader check accepts a leader recognised as either `codex` or `omx` — team workers run plain Codex, and a hand-started leader may be either. The cleanup loop stays first-Adapter-wins in registry order.
- **Setup and teardown are truly per kind.** The OMX-on-ZFS session-pointer cleanup lives on `adapters.omx`; a plain Codex stop runs no teardown.
