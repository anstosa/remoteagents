# Claude inline questions ride the reported-state channel

Codex agents already get their multiple-choice questions rendered in the console as an Inline question — numbered choice buttons answered with one tap — and Claude Code's `AskUserQuestion` dialog should get the same. The question's *content* is exact and structured in the hook the console already injects, so the console renders it from the reported hook payload rather than parsing the TUI: `rac-attention question --payload` base64-encodes the PreToolUse body into a new pane option `@rac_question` beside `@rac_attention`, the console reads it in the `list-panes -F` poll it already runs (ADR 0001), and a pure matcher on the Claude Adapter (`reportedClaudeQuestion(payload, capture)`) decodes it and confirms the dialog is still open with two presence checks built from the payload's own strings — the question text, and its first option drawn as the numbered row `1. <label>` — within the last 80 lines of the pane's capture. We chose this because ADR 0001 reserved a payload channel for exactly this case, the payload cannot misparse and carries option descriptions for later, it reaches the dashboard so a push notification can name the question, and answering still sends keys the way Codex does (`selectOption`: Down × index, Enter) since both probe runs confirmed the dialog draws options in payload order with the highlight on the first.

## Considered options

- **A pure pane parser.** Rejected: every rendering detail it would key on is cosmetic and changes without notice (Claude Code shipped three versions in three days on this host), it fails silently, and a misparse can shift the Down count and pick the wrong option. The repo already retreated from TUI parsing once — native Codex turn completion moved to the rollout log (ADR 0002). The reserved parsed fallback for hand-started sessions without hooks stays a possible follow-up, not the primary path.
- **An HTTP hook posting the question to the console.** Payload-rich, but every hook config would need the console's address and a token, the question would live only in console memory, and a sandboxed agent would need the console host allow-listed — the same reasons ADR 0001 kept the pane-option channel over HTTP.
- **Trusting the payload alone, without the capture checks.** The payload cannot say whether the dialog is still open: an Esc cancel fires **no hook at all**, so `@rac_question` lingers, and the transcript above repeats every answered or declined question's text. Neither the "User answered" nor the "User declined" summary draws a numbered option row, so the row check is what tells a live dialog from its own scrollback.

## Consequences

- **One new pane option, cleared like the others.** `@rac_question` holds the base64 payload (newlines stripped so the `list-panes` line stays tab-safe) or the empty string; every `rac-attention` invocation without `--payload` clears it, and the console unsets it with the other `@rac_*` options when the pane's agent process disappears. An oversize payload (over 64 KiB) is dropped but the state still reports.
- **`PreToolUse` splits by tool.** `AskUserQuestion` reports `question --payload`; `ExitPlanMode` reports `question` only. The golden `hooks.json` is re-pinned.
- **The raw payload stays server-side.** Discovery keeps it per agent id beside the reported-attention map and attaches the derived question to the Agent in `buildDashboard` — one pane capture per dashboard build per agent currently holding a payload. It never rides the published `Agent`. Answering re-derives the question from a fresh payload and capture and compares ids, so a payload cleared by PostToolUse, a cancelled dialog, or a dialog that advanced between render and tap is refused.
- **Single-choice questions only, across as many as the call carries.** A call with several questions is walked one tab at a time: only the active tab draws its text and rows, so exactly one of the payload's questions is live in the capture, and the matcher renders it — advancing to the next as each is answered. After the last answer the review page repeats every question's text with its answer, so it is matched by its own literal (`Ready to submit your answers?` with the `1. Submit answers` row) before any question text and rendered as a `{Submit answers, Cancel}` question that `selectOption(0)` submits. Two questions that share a text and first option are indistinguishable on screen and render nothing, as does an answered or cancelled call. Still follow-ups: a multiSelect question (Space/Enter toggle, submit through a separate tab), an option-less text/number question, the free-text `Type something.` row, and option descriptions in the web.
- **Answering assumes the caret opens on the first option.** `selectOption` sends Down × index then Enter, so it depends on the dialog's highlight starting on row 1 — which both probe runs confirmed for a freshly opened dialog. The row check confirms option order (option 1 is *drawn* as `1. <label>`), not caret position: `normalize` strips the `❯` caret, so the check matches whether or not the caret sits on row 1. A human co-driving the same pane could move the caret before the console's keys arrive (a captured `other-focused` probe shows a renderable dialog with the caret on the free-text row), which would misselect; homing the caret first needs a key sequence the probe has not verified, so it stays a follow-up. Answering without attaching to the pane — the feature's purpose — is safe.
